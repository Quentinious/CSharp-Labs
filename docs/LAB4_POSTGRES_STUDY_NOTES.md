# Лабораторная работа №4: сохранение семестра в PostgreSQL

## Задание и связь с предыдущими работами

ЛР №1 задала правила игры, историю и обучающуюся стратегию. ЛР №2 добавила
Generic Host, DI, интервал между днями и остановку по клавише. ЛР №3 отделила
источник случайности через `IRandomSource` и проверила правила unit-тестами.
ЛР №4 сохраняет каждый законченный день в настоящую PostgreSQL и позволяет
продолжить незавершённый семестр после закрытия приложения.

Аудит перед реализацией показал:

- solution содержит `Csharp` и `Csharp.Tests`, оба на .NET 10;
- `--semester` запускает один семестр, `--benchmark` — оценку стратегии;
  без аргументов работают прежние `SimulationService`, `SimulationWorker`
  и `KeyboardStopService` с интервалом 5 секунд;
- DI прежнего режима создаёт singleton-фабрику, стратегию, случайность и сервис;
  сервис владеет одним `DaySimulationEngine`;
- движок хранит удовольствие, следующий день, вылет и `StudentHistory`;
- фабрика использует случайность для правила и обеих зависимостей;
  преподаватели используют её только для `Check50`;
- стратегия хранит веса гипотез и `_processedDays`, но обновляет их строго
  по порядку прошлых дней, без случайности;
- `WasAsked` скрывает от стратегии вопросы на пропущенных парах, возвращая `null`;
  преподаватели читают фактические вопросы через `WasActuallyAsked`;
- день вылета раньше не добавлялся в историю. Теперь сохраняется его
  обработанная часть. Начисление очков, обнуление и немедленный вылет сохранены;
- до изменений реально было 28 тестовых случаев, а не ориентировочные 31.

План реализации: хранить правила, полную историю, прогресс, настройки стратегии
и состояние RNG; восстанавливать новые объекты; сохранять день транзакционно.
SQL находится только в отдельном репозитории. Классы правил и сама стратегия
для ЛР №4 не менялись. Прежние режимы не требуют подключения к БД.

## Добавленные классы и методы

| Класс | Назначение |
|---|---|
| `StatefulRandomSource` | Генератор SplitMix64 с сохраняемым 64-битным состоянием; реализует прежний `IRandomSource`. |
| `SemesterState`, `SavedDay` | Снимок сессии и результат сохранённого дня. Это данные, а не подключение к БД. |
| `SemesterSession` | Владеет движком, стратегией и RNG одного семестра; `CreateNew`, `SimulateDay`, `CaptureState`. Ограничивает семестр днями 0–99. |
| `ISemesterRepository` | Небольшой контракт: инициализировать, создать, сохранить день, загрузить, перечислить активные UUID. |
| `SemesterRepository` | Реализует контракт на Npgsql с параметризованным SQL и транзакциями. |
| `PersistentSimulationService` | Проводит и сохраняет день через `SimulateAndSaveDayAsync`. При ошибке запрещает дальнейший прогон в памяти. |
| `PersistentSimulationWorker` | Вызывает управляющий сервис каждые 5 секунд, печатает результат после COMMIT, останавливает Host в конце. |

`Program.RunPersistentAsync` разбирает новые аргументы, читает конфигурацию,
инициализирует БД и регистрирует сервисы нового режима. Используется прежний
`KeyboardStopService`. В `DaySimulationEngine` добавлен конструктор восстановления
и чтение прогресса/истории. `DayResult.Lessons` и `StudentHistory.Days` позволяют
собрать снимок, не раскрывая фактические вопросы через интерфейс стратегии.

## Таблицы и связи

Схема — [`Csharp/Persistence/schema.sql`](../Csharp/Persistence/schema.sql).
Она также встроена в сборку, поэтому `InitializeAsync` создаёт таблицы при запуске.
Скрипт повторно применим к исходной схеме ЛР №4, но не является системой миграций
для произвольных старых таблиц с совпадающими именами. Используйте отдельную БД.

| Таблица | Что хранит |
|---|---|
| `semesters` | UUID, время UTC, `active`/`completed`/`expelled`, `next_day`, удовольствие, вылет, `random_state`, версия RNG, период наблюдения и порог риска. |
| `semester_teachers` | Шесть исходных преподавателей: предмет, порядок обработки, правило, обе зависимости, включая неиспользуемые для `Check50`. |
| `simulation_days` | Номер дня, накопленное удовольствие после дня и вылет. |
| `lesson_results` | Предмет, присутствие и фактический вопрос для обработанного занятия. |

Один семестр имеет много преподавателей и дней. Каждое занятие ссылается на день
по `(semester_id, day)` и на преподавателя по `(semester_id, subject)`.
Первичный ключ `(semester_id, day, subject)` запрещает дубликаты предмета в день.
Порядок преподавателей сохраняется отдельно: он важен для потребления RNG
и неполного дня вылета. Ограничения проверяют диапазоны, статусы и нулевой счёт
при вылете. Индексы начинаются с внешних ключей.

`next_day` всегда обозначает **первый ещё не проведённый день**:
при создании 0; после сохранения дня 0 — 1; после дня 99 — 100.
Вылетевшие сессии тоже сохраняют следующий номер, но статус запрещает продолжение.

## Сохранение дня и транзакция

```text
SimulateDay()
     |
     v
DaySimulationResult + обработанные занятия + состояние RNG
     |
     v
PersistentSimulationService -> SemesterRepository.SaveDayAsync
     |
     v
PostgreSQL
     |
     v
SemesterRepository.LoadAsync
     |
     v
SemesterSession -> новый DaySimulationEngine
     |
     v
SimulateDay() следующего дня
```

1. `SimulateDay` принимает решение по всем предметам и проводит занятия до конца
   дня либо до первого вылета. При вылете удовольствие обнуляется.
2. `SaveDayAsync` открывает транзакцию и блокирует строку сессии через
   `SELECT ... FOR UPDATE`. Проверяет статус `active` и ожидаемый номер дня.
3. Вставляет день и только обработанные занятия.
4. Обновляет удовольствие, `next_day`, статус и состояние RNG.
5. Делает COMMIT. Только после этого worker выводит результат.

Транзакция нужна, чтобы состояние не стало наполовину новым: день, занятия
и прогресс либо сохраняются вместе, либо откатываются вместе. Исключение,
отмена или разрыв соединения до фиксации приводят к откату. Если ответ COMMIT
потерян и его исход неизвестен, приложение останавливается: следующий запуск
читает фактический результат из БД. Продолжать непроверенный прогресс в памяти
нельзя. Блокировка и проверка номера дня защищают также от двух одновременно
запущенных процессов: устаревший процесс завершится с ошибкой сохранения.

## Восстановление истории, стратегии и случайности

`LoadAsync` читает все таблицы в транзакции `RepeatableRead`: даже при параллельной
записи все SELECT видят один снимок. Метод проверяет число преподавателей,
непрерывность дней и соответствие истории прогрессу. Отсутствующий UUID даёт `null`;
приложение объясняет ошибку и не создаёт подменяющий новый семестр.

`SemesterSession` создаёт новые `StudentHistory`, `StudentStrategy`, RNG и движок.
История заполняется днями в исходном порядке; фактические вопросы сохраняются,
но стратегия по-прежнему видит только разрешённые наблюдения.

Стратегия восстанавливается по варианту A, без сериализации массивов весов.
На первом `DecideDay(next_day, history)` её `ProcessNewHistory` обрабатывает дни
0…next_day−1 в том же порядке и теми же арифметическими операциями. Неважно,
поступили эти дни по одному во время прогона или одним набором из БД: обновление
весов использует только текущий обрабатываемый день и предыдущий. Период
наблюдения и порог риска загружаются из `semesters`. Веса и `_processedDays`
до первого решения могут ещё не быть вычислены, но перед решением получаются
ровно те же значения. Саму логику `StudentStrategy` менять не потребовалось.

Для вопросов используется SplitMix64 v1. Внутреннее состояние целиком помещается
в `bigint`; отрицательные значения — нормальное представление 64 бит, не ошибка.
На каждом вызове обновляется состояние; `Next(maxValue)` использует rejection
sampling, чтобы не вносить смещение остатком от деления. Новый seed берётся из
`RandomNumberGenerator`, поэтому настоящие семестры не используют тестовую
фиксированную последовательность. Создание преподавателей использует отдельный
генератор. При восстановлении фабрика не вызывается; RNG вопросов продолжается
с сохранённого состояния. Алгоритм не зависит от внутренностей `System.Random`.
В БД хранится `random_version = 1`: менять алгоритм без поддержки старых версий
нельзя. Аналогично изменение обучения стратегии потребует учёта старых сохранений.

Равенство продолжения обеспечивают пять вещей: исходные правила и их порядок,
полная история с прежней видимостью, те же настройки и алгоритм обучения,
точное состояние RNG, а также начало с `next_day` без повторного начисления очков.

## Запуск PostgreSQL

Все команды ниже выполняются из корня репозитория в PowerShell.

### Вариант 1: Docker Compose

Пароль задайте локально, не добавляйте его в исходники:

```powershell
$env:POSTGRES_PASSWORD = Read-Host 'Пароль локальной PostgreSQL'
docker compose up -d --wait
$env:ConnectionStrings__Postgres = "Host=127.0.0.1;Port=55432;Database=csharp_labs;Username=lab4;Password=$env:POSTGRES_PASSWORD"
```

Данные сохраняются в отдельном Docker volume `lab4_postgres`. Обычная остановка:
`docker compose stop`. Для сохранности данных не удаляйте volume.

### Вариант 2: установленный PostgreSQL

При необходимости добавьте каталог PostgreSQL `bin` в PATH. Через psql под
администратором создайте отдельного пользователя и две базы:

```powershell
psql -U postgres -d postgres
```

```sql
CREATE ROLE lab4 LOGIN;
\password lab4
CREATE DATABASE csharp_labs OWNER lab4;
CREATE DATABASE csharp_labs_tests OWNER lab4;
\q
```

`\password` интерактивно запросит пароль, не помещая его в SQL-файл.

```powershell
$lab4Password = Read-Host 'Пароль пользователя lab4'
$env:ConnectionStrings__Postgres = "Host=127.0.0.1;Port=5432;Database=csharp_labs;Username=lab4;Password=$lab4Password"
```

Таблицы создаются автоматически первым режимом ЛР №4. Альтернативно примените
тот же скрипт вручную (psql запросит пароль):

```powershell
psql -h 127.0.0.1 -p 5432 -U lab4 -d csharp_labs -f Csharp/Persistence/schema.sql
```

Для Docker используйте `-p 55432`. Npgsql читает строку из конфигурации .NET
`ConnectionStrings:Postgres`; переменная `ConnectionStrings__Postgres` задаёт
тот же ключ. Настоящие пароли не записаны в репозиторий.

## Запуск, остановка и продолжение

```powershell
dotnet restore Csharp.sln
dotnet build Csharp.sln --no-restore
dotnet run --project Csharp --no-build -- --new-semester
```

Запишите напечатанный UUID. Каждые 5 секунд сохраняется день. Нажмите любую
клавишу или Ctrl+C, затем убедитесь, что процесс завершился. В перенаправленной
консоли обработчик клавиш отключён; Ctrl+C работает в обычном терминале.

```powershell
dotnet run --project Csharp --no-build -- --list-semesters
dotnet run --project Csharp --no-build -- --resume-semester <UUID-из-вывода>
```

Замените `<UUID-из-вывода>` настоящим UUID без угловых скобок. При нескольких
активных сессиях всегда нужен явный UUID. Новая сессия создаёт новую строку,
не перезаписывая старые. После вылета или дня 99 продолжение запрещено;
в списке активных таких сессий нет.

Прежние запуски работают без переменной PostgreSQL:

```powershell
dotnet run --project Csharp --no-build -- --semester
dotnet run --project Csharp --no-build -- --benchmark
dotnet run --project Csharp --no-build
```

## Интеграционные и unit-тесты

Unit-тесты проверяют правила/стратегию/движок в памяти с тестовой случайностью.
Интеграционные тесты выполняют настоящий SQL, COMMIT, чтение новых объектов,
проверку ограничений и ROLLBACK на реальном сервере PostgreSQL.

В этой реализации выбран разрешённый заданием вариант отдельной тестовой БД:
на машине проверки Docker отсутствовал. Дополнительная библиотека Testcontainers
не требуется. Если Docker есть, тестовую БД можно создать в Compose-контейнере:

```powershell
docker compose exec postgres createdb -U lab4 -O lab4 csharp_labs_tests
$env:LAB4_TEST_POSTGRES = "Host=127.0.0.1;Port=55432;Database=csharp_labs_tests;Username=lab4;Password=$env:POSTGRES_PASSWORD"
dotnet test Csharp.sln --no-restore
dotnet test Csharp.sln --no-restore --filter 'Category=Integration'
dotnet test Csharp.sln --no-restore --filter 'Category!=Integration'
```

Для установленного сервера используйте свою тестовую базу и порт 5432.
`LAB4_TEST_POSTGRES` должна указывать именно на тестовую БД, отдельно от
`ConnectionStrings__Postgres`. Учётной записи нужны права создавать схемы.
Fixture создаёт уникальную схему `lab4_test_<UUID>` и устанавливает `SearchPath`.
После тестов удаляет только свою схему; пользовательские таблицы не очищаются.
Без `LAB4_TEST_POSTGRES` интеграционные проверки явно помечаются как пропущенные.
Это не считается их успешным прохождением.

| Сценарий | Проверка |
|---|---|
| `SaveAndLoad_RestoresState` | Прогресс, конфигурация, шесть правил с зависимостями, все занятия, RNG; чтение новым репозиторием. |
| `Resume_MatchesContinuousRun` | Три остановки после 9, 10, 14 дней; новый движок/стратегия/RNG, сравнение до дня 39, включая решения и оба исхода `Check50`. |
| `CompletedSemester_CannotResume` | Отдельно вылет с неполным днём и все 100 дней; запрет продолжения и сохранения. |
| `Sessions_AreIndependent` | Два UUID с разными правилами и количеством дней не смешиваются. |
| `SaveFailure_RollsBack` | Шестое занятие нарушает FK после пяти успешных вставок; нет ни дня, ни занятий, ни обновления RNG/прогресса; корректная повторная запись проходит. |
| `MissingSemester_ReturnsNull` | Несуществующий UUID не превращается в новую сессию. |

Дополнительно в тесте продолжения повторная запись старого дня отвергается.
Сравниваются все сохранённые результаты; неполный день вылета не дополняется
фиктивными занятиями. В тестах фиксирован seed только для воспроизводимости;
используется настоящий семестровый `StatefulRandomSource`, а не список чисел.

## Просмотр данных через SQL

Подключение: `psql -h 127.0.0.1 -p 55432 -U lab4 -d csharp_labs`
(для установленного сервера подставьте его порт).

```sql
SELECT id, created_at, status, next_day, total_pleasure, expelled,
       random_state, observation_days, risk_threshold
FROM semesters ORDER BY created_at;

-- В psql задайте UUID интересующей сессии:
\set session_id 'вставьте-настоящий-UUID'

SELECT subject, position, rule, depend_a, depend_b
FROM semester_teachers WHERE semester_id = :'session_id' ORDER BY position;

SELECT day, total_pleasure, expelled
FROM simulation_days WHERE semester_id = :'session_id' ORDER BY day;

SELECT day, subject, attended, was_actually_asked
FROM lesson_results WHERE semester_id = :'session_id' ORDER BY day, subject;

-- Число уникальных дней должно равняться next_day; дубликаты запрещены PK:
SELECT s.id, s.next_day, count(d.day) AS saved_days
FROM semesters s LEFT JOIN simulation_days d ON d.semester_id = s.id
GROUP BY s.id;
```

Нумерация предметов: 0 Calculus, 1 LinearAlgebra, 2 DiscreteMath, 3 Programming,
4 Physics, 5 English. Правила: 0 Check50, 1 DependA, 2 XorAandB.

## Как защищать работу

1. Покажите `--new-semester`, UUID и сохранённые строки одного дня в psql.
2. Остановите процесс клавишей. Покажите `next_day` и исходные правила.
3. Запустите `--resume-semester UUID`: первый выведенный день должен совпасть
   с прежним `next_day`. Правила не меняются, старые дни не дублируются.
4. Объясните разделение: движок моделирует, управляющий сервис сохраняет,
   репозиторий знает SQL, worker управляет временем и выводом.
5. Объясните, почему одного счёта и seed недостаточно: нужны история обучения
   и текущая позиция RNG. Здесь история переобучает стратегию, а RNG хранит состояние.
6. Покажите интеграционный тест продолжения и тест отката. Объясните, что
   подключение к настоящей БД проверяет то, чего не проверяет мок-репозиторий.
7. Покажите две причины запрета продолжения: `expelled` и `next_day = 100`.

Проект намеренно не вводит ORM, CQRS, миграционный фреймворк и хранение весов
в JSON: для 100 дней достаточно простой схемы, Npgsql и восстановления по истории.
Это сохранения между днями; середина занятия отдельно не сохраняется.
