# Учебный конспект по лабораторной работе №1

Конспект составлен по актуальным `req.txt`, всем файлам `.cs` и `Csharp.csproj`. Текущая программа уже работает на новой архитектуре. Старый вариант упоминается только в разделе «было → стало».

# 1. Суть лабораторной

Симуляция описывает семестр из 100 учебных дней. Каждый день у студента шесть пар:

1. `Calculus`;
2. `LinearAlgebra`;
3. `DiscreteMath`;
4. `Programming`;
5. `Physics`;
6. `English`.

У каждого преподавателя есть одно из трёх правил:

- `Check50` — спросить с вероятностью 50%;
- `DependA` — спросить, если вчера спрашивали по предмету A;
- `XorAandB` — спросить, если вчера спрашивали ровно по одному из предметов A и B.

A и B случайно выбираются при создании преподавателя. Они могут совпасть с его собственным предметом, но не могут совпадать друг с другом.

Каждый день студент получает `+1` удовольствия за пирожок. За каждую пропущенную пару он получает ещё `+1`. Если студент прогулял и преподаватель его спросил, студент вылетает, а итог семестра становится равен нулю.

Цель стратегии — выбирать посещение так, чтобы получить высокий средний результат, не вылетая.

# 2. Что потребовал преподаватель дополнительно

| Требование | Смысл | Зачем оно нужно |
|---|---|---|
| .NET 10 | Проект собирается под `net10.0` | Все стратегии запускаются в одинаковой среде |
| `ISkipStrategy` | Общий контракт стратегии | Runner не зависит от конкретного алгоритма |
| `Name` | Название стратегии | Результат можно подписать |
| `DecideDay` | Одно решение сразу на день | Сегодняшние исходы не влияют на решения того же дня |
| `IReadOnlyStudentHistory` | Ограниченное представление истории | Стратегия видит только допустимые сведения |
| `Attended` | Был ли студент на паре | Стратегия знает свои прошлые действия |
| `WasAsked` | Наблюдаемый исход опроса | Скрытый исход прогулки не раскрывается |
| Один вызов в начале дня | `DecideDay` вызывается до опросов | Все шесть решений фиксируются заранее |
| `true` / `false` | `true` — идти, `false` — прогулять | У массива решений один понятный смысл |
| 1000 итераций | Среднее по множеству семестров | Один случайный семестр не искажает оценку |
| Менее 10 минут | Ограничение на 1000 запусков | Стратегия должна работать быстро |
| Без внешних NuGet-пакетов | Только стандартные возможности .NET | Работы проще собирать общим runner-ом |
| Отдельный проект стратегии | Отдельный `.csproj` | Стратегия физически не получает внутренние типы runner-а |

В `req.txt` также сказано, что отдельного таймаута на `DecideDay` нет. Это не разрешение выполнять тяжёлые вычисления: общий лимит 1000 итераций всё равно остаётся.

# 3. Что было не так с первой реализацией

Этот раздел описывает прошлую версию, а не текущий код.

## StudentStrategy видел Teacher

Раньше связь выглядела так:

    StudentStrategy
          |
          v
       Teacher
          |- Rule
          |- DependA
          |- DependB
          `- GetAskProbability

Получив `Teacher`, стратегия могла узнать правило, A/B и точную вероятность опроса. Но студент по условию не знает внутренние настройки преподавателя. Он может опираться только на то, что наблюдал раньше.

Теперь `StudentStrategy` получает `IReadOnlyStudentHistory`, а `Teacher` в его сигнатуре отсутствует.

## ShouldSkip вызывался для каждой пары

Раньше решение принималось шесть раз за день — отдельно перед каждой парой. Это плохо выражало требование «решить всё в начале дня» и позволяло архитектуре смешивать принятие решений с расчётом сегодняшних исходов.

Теперь `DecideDay` вызывается ровно один раз, возвращает шесть значений, и только после этого симулятор вызывает преподавателей.

## yesterdayAsked / todayAsked

`bool[]` не плох сам по себе: он по-прежнему уместен как заданный контрактом массив решений на один день. Но для истории такой массив слишком невыразителен:

- не хранит номер дня;
- не хранит присутствие;
- связывает предмет с неочевидным индексом;
- не различает фактический исход и знания студента;
- не может выразить «результат неизвестен».

Теперь история состоит из предметных объектов.

| Было | Стало | Почему стало лучше |
|---|---|---|
| `ShouldSkip(Teacher, bool[])` | `DecideDay(int, IReadOnlyStudentHistory)` | Стратегия не получает Teacher |
| Шесть решений по очереди | Один массив решений в начале дня | Сегодняшние результаты ещё неизвестны |
| `yesterdayAsked` / `todayAsked` | `StudentHistory` | Хранится история всех завершённых дней |
| Один массив фактов | `LessonResult` и `DayResult` | Явно представлены пара и день |
| Только `true/false` | `bool? WasAsked` | Можно выразить неизвестный исход через `null` |
| `Run()` возвращал `int` | `SemesterResult` | Удовольствие и вылет разделены |
| Один семестр | 1000 независимых семестров | Получается средняя оценка стратегии |

# 4. Общая архитектура текущей версии

Фактические зависимости:

    Program
      |
      +--> TeacherFactory --> Teacher[6]
      |
      +--> StudentStrategy : ISkipStrategy
      |
      `--> SemesterSimulator
             |- ISkipStrategy
             |- StudentHistory
             |     `--> List<DayResult>
             |             `--> Dictionary<Subject, LessonResult>
             |- Teacher[]
             `- SemesterResult

## Реальный мир симулятора

Симулятор и Teacher должны знать фактический результат:

    LessonResult.WasActuallyAsked
                  |
                  v
    StudentHistory.WasActuallyAsked(...)
                  |
                  v
    Teacher.GetAskProbability(...)

Это необходимо для правил `DependA` и `XorAandB`.

## То, что может видеть стратегия

Стратегия получает только интерфейс:

    IReadOnlyStudentHistory
        |- Attended(...)
        `- WasAsked(...) -> bool?
                  |
                  v
        StudentStrategy.DecideDay(...)

Если студент отсутствовал, `WasAsked` возвращает `null`, даже если симулятор знает фактический `true` или `false`.

Граница проводится типом параметра `IReadOnlyStudentHistory`: в API стратегии нет Teacher, TeacherRule, A/B и `WasActuallyAsked`.

# 5. Разбор каждого файла

## 5.1. Subject.cs

### Зачем он существует

Задаёт единый набор учебных предметов.

### Что в нём находится

Публичный enum `Subject` с шестью значениями.

### Разбор основных членов

~~~csharp
public enum Subject
{
    Calculus,
    LinearAlgebra,
    DiscreteMath,
    Programming,
    Physics,
    English
}
~~~

Значения автоматически получают номера `0`–`5`. Эти номера используются как индексы массива дневных решений.

### С кем связан

С `Teacher`, `TeacherFactory`, `DayResult`, историей и контрактами стратегии.

### Что важно на защите

- enum не позволяет придумать несуществующий предмет;
- порядок enum совпадает с порядком решений;
- старого второго enum в `Program.cs` больше нет;
- это публичная часть конкурсного контракта.

## 5.2. StrategyContracts.cs

### Зачем он существует

Определяет публичный контракт между runner-ом и стратегией.

### Что в нём находится

- `ISkipStrategy`;
- `IReadOnlyStudentHistory`.

### Основные члены

`ISkipStrategy.Name` возвращает имя.

`DecideDay(int day, IReadOnlyStudentHistory history)` получает день и прошлую доступную историю, возвращает `bool[]`.

`Attended` сообщает присутствие. `WasAsked` возвращает наблюдаемый результат или `null`.

### С кем связан

`StudentStrategy` реализует `ISkipStrategy`; `StudentHistory` реализует `IReadOnlyStudentHistory`; `SemesterSimulator` хранит стратегию через интерфейс.

### Что важно на защите

- интерфейс задаёт форму взаимодействия, а не алгоритм;
- `true` в решении означает посещение;
- стратегия получает только безопасную историю;
- оба интерфейса реально используются.

## 5.3. LessonResult.cs

### Зачем он существует

Хранит результат одной пары.

### Что в нём находится

`internal sealed class LessonResult`.

### Основные члены

- `Attended` — пришёл ли студент;
- `WasActuallyAsked` — спросил ли Teacher на самом деле;
- конструктор сохраняет оба значения.

Свойства имеют только `get`, поэтому результат после создания не меняется обычным присваиванием.

### С кем связан

Создаётся `SemesterSimulator`, хранится в `DayResult`, читается `StudentHistory`.

### Что важно на защите

- одна пара — один `LessonResult`;
- присутствие и опрос — разные факты;
- `WasActuallyAsked` относится к реальному миру;
- стратегия не получает объект напрямую.

## 5.4. DayResult.cs

### Зачем он существует

Собирает результаты всех предметов одного дня.

### Что в нём находится

~~~csharp
private readonly Dictionary<Subject, LessonResult> _lessons = new();
~~~

Также есть `Day`, `LessonCount`, `Add` и `GetLesson`.

### Основные члены

Конструктор сохраняет номер дня. `Add` связывает предмет с результатом пары. `GetLesson` возвращает результат по предмету. `LessonCount` позволяет проверить, что записаны все шесть пар.

### С кем связан

Создаётся симулятором и после полного дня добавляется в `StudentHistory`.

### Что важно на защите

- `LessonResult` — одна пара, `DayResult` — целый день;
- словарь делает связь с предметом явной;
- повторно добавить один предмет нельзя;
- история принимает только полный последовательный день.

## 5.5. StudentHistory.cs

### Зачем он существует

Хранит все завершённые дни и разделяет фактическую и наблюдаемую историю.

### Что в нём находится

- `List<DayResult> _days`;
- публичные `Attended` и `WasAsked`;
- внутренние `WasActuallyAsked` и `Add`;
- приватный `GetDay`.

### Основные члены

`Attended` возвращает факт присутствия.

`WasAsked` скрывает исход прогулки:

~~~csharp
if (!lesson.Attended)
{
    return null;
}
return lesson.WasActuallyAsked;
~~~

`WasActuallyAsked` возвращает реальный исход для Teacher. `Add` проверяет правильный номер дня и наличие всех шести пар. `GetDay` проверяет диапазон.

### С кем связан

Реализует `IReadOnlyStudentHistory`, создаётся `SemesterSimulator`, читается Teacher и передаётся стратегии как интерфейс.

### Что важно на защите

- один объект хранит факты, но наружу отдаёт ограниченное представление;
- отсутствовавший студент получает `null`;
- Teacher читает реальный результат;
- история содержит только полностью законченные дни.

## 5.6. Teacher.cs

### Зачем он существует

Хранит скрытые параметры преподавателя и рассчитывает опрос.

### Что в нём находится

Enum `TeacherRule` и класс `Teacher`.

### Основные члены

Свойства:

- `Subject`;
- `Rule`;
- `DependA`;
- `DependB`.

`GetAskProbability(int day, StudentHistory history)` возвращает `0`, `0.5` или `1`.

`WillAsk` превращает вероятность в конкретный `bool`: ноль — нет, один — да, половина — случайный выбор.

### С кем связан

Создаётся фабрикой, вызывается симулятором, читает фактическую историю.

### Что важно на защите

- Teacher больше не принимает массив вчерашних результатов;
- при `day == 0` зависимые правила получают ноль;
- `Check50` остаётся случайным и в первый день;
- стратегия Teacher не получает;
- Teacher использует `WasActuallyAsked`, а не публичный `WasAsked`.

## 5.7. TeacherFactory.cs

### Зачем он существует

Создаёт полный набор случайных преподавателей.

### Что в нём находится

Статический класс с `CreateTeachers` и приватными методами случайного выбора.

### Основные члены

`CreateTeachers` перебирает `Enum.GetValues<Subject>()`, выбирает правило, A и B и создаёт Teacher. В `GetRandomDifferentSubject` B перевыбирается в цикле, пока не станет отличаться от A.

### С кем связан

Вызывается `Program`, использует `Random`, `Subject`, `TeacherRule`, возвращает `Teacher[]`.

### Что важно на защите

- создаётся один Teacher на предмет;
- A/B выбираются даже для `Check50`, но там не влияют на результат;
- A или B могут совпасть с собственным предметом;
- `B != A` гарантирует цикл;
- фабрика вызывается заново в каждой итерации.

## 5.8. StudentStrategy.cs

### Зачем он существует

Содержит текущую baseline-стратегию.

### Что в нём находится

~~~csharp
public sealed class StudentStrategy : ISkipStrategy
~~~

Свойство `Name` и метод `DecideDay`.

### Основные члены

Метод узнаёт количество предметов, создаёт массив и записывает `true` во все элементы:

~~~csharp
for (var i = 0; i < attendance.Length; i++)
{
    attendance[i] = true;
}
~~~

Параметры `day` и `history` пока не используются, но входят в контракт и позволят позже написать более умную стратегию.

### С кем связан

Реализует `ISkipStrategy`, создаётся `Program`, вызывается `SemesterSimulator`.

### Что важно на защите

- `true` означает идти;
- стратегия посещает все шесть пар;
- в ней нет Teacher, Rule и A/B;
- она легальна, безопасна и намеренно не оптимальна;
- алгоритм можно заменить без изменения симулятора.

## 5.9. SemesterResult.cs

### Зачем он существует

Явно описывает итог одного семестра.

### Что в нём находится

~~~csharp
internal sealed record SemesterResult(int Pleasure, bool Expelled);
~~~

### Основные члены

Record автоматически получает конструктор и свойства `Pleasure`, `Expelled`.

### С кем связан

Возвращается `SemesterSimulator.Run` и обрабатывается `Program`.

### Что важно на защите

- нулевой результат и факт вылета представлены отдельно;
- `Program` считает вылеты по `Expelled`;
- объект маленький и неизменяемый;
- `Run` действительно возвращает этот тип.

## 5.10. SemesterSimulator.cs

### Зачем он существует

Проводит один семестр от дня 0 до дня 99.

### Что в нём находится

- `SemesterDays = 100`;
- `_teachers`;
- `_strategy` типа `ISkipStrategy`;
- `_rand`;
- конструктор;
- `Run`;
- приватный `ValidateAttendance`.

### Основные члены

Конструктор получает зависимости. `Run` создаёт чистый `StudentHistory`, вызывает стратегию, рассчитывает опросы, строит результаты и возвращает `SemesterResult`.

`ValidateAttendance` проверяет:

- массив не равен `null`;
- длина равна количеству предметов.

### С кем связан

Получает Teacher и стратегию от `Program`, создаёт историю и дневные результаты, вызывает Teacher, возвращает результат семестра.

### Что важно на защите

- `DecideDay` находится ровно один раз в цикле дня;
- он вызывается до `Teacher.WillAsk`;
- индекс решения получается через `(int)teacher.Subject`;
- день добавляется в историю после всех пар;
- вылет немедленно возвращает `SemesterResult(0, true)`.

## 5.11. Program.cs

### Зачем он существует

Собирает приложение, запускает 1000 семестров и печатает статистику.

### Что в нём находится

`SimulationCount = 1000` и `Main`.

### Основные члены

`Main` создаёт `Random`, запускает `Stopwatch`, затем 1000 раз:

1. создаёт новых Teacher;
2. создаёт новую стратегию через `ISkipStrategy`;
3. создаёт новый `SemesterSimulator`;
4. вызывает `Run`;
5. суммирует удовольствие и вылеты.

После цикла рассчитываются средние значения и процент вылетов.

### С кем связан

С `TeacherFactory`, `ISkipStrategy`, `StudentStrategy`, `SemesterSimulator`, `SemesterResult` и `Stopwatch`.

### Что важно на защите

- старого enum здесь больше нет;
- каждый семестр получает новых Teacher;
- история чистая, потому что создаётся внутри нового `Run`;
- стратегия создаётся заново;
- выводится среднее по 1000 итерациям, а не результат одного семестра.

# 6. Особо подробно: новая модель истории

    LessonResult
          |
          v
      DayResult
          |
          v
    StudentHistory
          |
          | как IReadOnlyStudentHistory
          v
    StudentStrategy

Допустим, день содержит:

    Calculus:
        Attended = true
        WasActuallyAsked = false

    Physics:
        Attended = false
        WasActuallyAsked = false

Симулятор знает оба фактических результата. Для Physics:

~~~csharp
history.WasActuallyAsked(day, Subject.Physics) // false
~~~

Но стратегия получает:

~~~csharp
history.Attended(day, Subject.Physics) // false
history.WasAsked(day, Subject.Physics) // null
~~~

## Зачем нужен bool?

`bool?` имеет три состояния:

| Значение | Значение в задаче |
|---|---|
| `true` | Студент был и его спросили |
| `false` | Студент был и его точно не спросили |
| `null` | Студент отсутствовал и не знает исход |

`false` — известный отрицательный факт. `null` — отсутствие доступной информации.

Teacher нужна фактическая история, потому что правила зависят от того, что произошло на самом деле. Стратегия не должна видеть `WasActuallyAsked`, иначе она узнает события с пропущенных пар.

Если отсутствующего студента фактически спросили, симулятор сразу завершает семестр. Такой неполный день в историю не добавляется, потому что следующего решения уже не будет.

# 7. Особо подробно: один день работы программы

Фактическая последовательность в `Run`:

1. Начинается очередной `day`.
2. Один раз вызывается `_strategy.DecideDay(day, history)`.
3. В `history` находятся только полностью завершённые прошлые дни.
4. Стратегия возвращает решения для шести Subject.
5. `ValidateAttendance` проверяет `null` и длину.
6. Создаётся пустой `DayResult`.
7. Добавляется `+1` за пирожок.
8. Для каждого Teacher читается решение по индексу предмета.
9. Teacher определяет фактический `asked`.
10. Создаётся `LessonResult`.
11. Результат добавляется в `DayResult`.
12. При прогулке добавляется удовольствие; прогулка плюс опрос немедленно даёт вылет.
13. После всех шести пар полный `DayResult` добавляется в `StudentHistory`.

Ключевой порядок:

    DecideDay для всех предметов
             |
             v
    расчёт сегодняшних опросов

Поэтому стратегия не может увидеть результат первой сегодняшней пары перед решением по второй: весь массив уже возвращён.

# 8. Особо подробно: один полный семестр

    Day 0
      |
    Day 1
      |
     ...
      |
    Day 99
      |
    SemesterResult

`pleasure` — локальная переменная `Run`. Каждый день добавляет пирожок, каждая прогулка — ещё единицу.

Если студент отсутствует и `asked == true`, метод немедленно возвращает:

~~~csharp
new SemesterResult(0, true)
~~~

Если все 100 дней закончены:

~~~csharp
new SemesterResult(pleasure, false)
~~~

Baseline всегда присутствует, поэтому проходит все 100 дней, получает 100 пирожков и не вылетает.

# 9. Как работают правила Teacher после рефакторинга

## Check50

Всегда возвращает вероятность `0.5`, включая день 0. `WillAsk` использует `rand.Next(2) == 0`.

Пример: Teacher по Programming имеет `Check50`; вчерашняя история на решение не влияет.

## DependA

После первого дня читает:

~~~csharp
history.WasActuallyAsked(day - 1, DependA)
~~~

Пример: Physics зависит от Programming. Если вчера по Programming фактически спрашивали, Physics сегодня спросит гарантированно; иначе не спросит.

## XorAandB

Teacher получает два фактических значения и сравнивает:

~~~csharp
askedDependA != askedDependB
~~~

| A вчера | B вчера | Сегодня спросит |
|---|---|---|
| `false` | `false` | нет |
| `true` | `false` | да |
| `false` | `true` | да |
| `true` | `true` | нет |

## День 0

Сначала обрабатывается `Check50`. Для остальных правил `day == 0` возвращает `0.0`, то есть считается, что вчера не спрашивали никого.

Teacher принимает конкретный внутренний `StudentHistory`, потому что ему нужен фактический исход. Стратегия получает другой тип параметра — публичный `IReadOnlyStudentHistory`.

# 10. Как работает текущая StudentStrategy

Текущая стратегия — простая baseline:

    true  = идти
    false = прогулять

Она записывает `true` для каждого Subject, поэтому посещает все пары.

За один семестр:

    100 дней × 1 пирожок = 100 удовольствия
    прогулок = 0
    вылетов = 0

Результаты опросов всё равно рассчитываются и записываются в историю, но при посещении они не приводят к вылету.

Стратегия намеренно не оптимальна. Её задача сейчас — показать законную архитектуру. Позже тело `DecideDay` можно заменить анализом `history`, не меняя runner.

# 11. Зачем нужен ISkipStrategy

    ISkipStrategy
          ^
          |
    StudentStrategy

Запись `StudentStrategy : ISkipStrategy` означает, что класс обязан реализовать `Name` и `DecideDay`.

`SemesterSimulator` хранит поле типа `ISkipStrategy`, поэтому ему не важно, какой конкретно класс передан. Преподаватель может подключить другую стратегию с тем же контрактом.

Стратегия зависит только от публичных `Subject`, `ISkipStrategy` и `IReadOnlyStudentHistory`, а не от Teacher и симулятора.

# 12. Зачем нужен IReadOnlyStudentHistory

    IReadOnlyStudentHistory
               ^
               |
         StudentHistory

Стратегия получает параметр интерфейсного типа. Интерфейс разрешает:

- узнать присутствие;
- узнать наблюдаемый результат.

Интерфейс не разрешает:

- получить `WasActuallyAsked`;
- добавлять дни;
- получить внутренние `DayResult`;
- узнать Rule и A/B.

Сам `StudentHistory` внутренний для runner-а. Это помогает позднее вынести стратегию в отдельную сборку.

# 13. 1000 итераций

Одна итерация в `Program` — один новый семестр:

1. новый набор случайных Teacher;
2. новый объект стратегии;
3. новый `SemesterSimulator`;
4. новая история внутри `Run`;
5. новый `SemesterResult`.

Один `Random` используется для всей серии, но каждая итерация продолжает его псевдослучайную последовательность и получает новые настройки.

Среднее удовольствие:

    сумма Pleasure / 1000

Среднее в день:

    среднее за семестр / 100

Процент вылетов:

    expelledSemesters / 1000

`Stopwatch` измеряет полный цикл. Свежий запуск:

~~~text
Количество семестров: 1000
Среднее удовольствие за семестр: 100,00
Среднее удовольствие в день: 1,00
Вылетов: 0 (0,00 %)
Общее время: 161 мс
~~~

161 мс значительно меньше 10 минут.

# 17. Основные C#-концепции, которые используются

## enum

`Subject` и `TeacherRule` задают ограниченные наборы значений.

## class

`Teacher`, `StudentHistory`, `SemesterSimulator` объединяют данные и методы.

## interface

`ISkipStrategy` и `IReadOnlyStudentHistory` задают доступные операции без раскрытия реализации.

## constructor

`new SemesterSimulator(teachers, strategy, rand)` передаёт зависимости при создании.

## property и get

`public string Name => ...` и `public Subject Subject { get; }` дают доступ к значениям без открытого setter-а.

## public, private, internal

- `public` — доступно внешней стратегии;
- `private` — только внутри класса;
- `internal` — только внутри сборки runner-а.

## static

`TeacherFactory` вызывается без создания объекта. `Main` — статическая точка входа.

## var

`var` выводит статический тип из правой части. Например, тип `result` — `SemesterResult`, а не динамическое значение.

## array

`bool[]` хранит шесть дневных решений. `Teacher[]` хранит преподавателей.

## List

`List<DayResult>` растёт по мере завершения дней.

## Dictionary

`Dictionary<Subject, LessonResult>` связывает предмет с результатом пары.

## bool? и nullable

`bool?` добавляет состояние `null`. В `.csproj` включён nullable-анализ.

## Casting enum → int

~~~csharp
attendance[(int)teacher.Subject]
~~~

Enum преобразуется в индекс массива.

## Dependency через constructor

Симулятор получает Teacher, стратегию и Random снаружи. Это позволяет заменять стратегию.

## Реализация интерфейса через `:`

`StudentStrategy : ISkipStrategy` и `StudentHistory : IReadOnlyStudentHistory`.

## readonly

Поля симулятора и коллекции истории нельзя переназначить после создания объекта.

## record

`SemesterResult` — компактный объект результата с автоматически созданными свойствами.

# 18. Вопросы, которые могут задать на защите

## 1. Почему StudentStrategy больше не получает Teacher?

Teacher раскрывает правило и A/B — сведения, которых студент не знает.

## 2. Зачем IReadOnlyStudentHistory?

Он показывает стратегии только разрешённые наблюдения.

## 3. Почему WasAsked возвращает bool??

Нужно выразить «да», «нет» и «неизвестно».

## 4. Чем null отличается от false?

`false` — известное отсутствие опроса; `null` — студент не мог наблюдать исход.

## 5. Зачем WasActuallyAsked?

Teacher должен применять правила к фактическим событиям, даже если студент отсутствовал.

## 6. Почему DecideDay вызывается один раз?

Чтобы все решения были приняты до сегодняшних опросов.

## 7. Почему сразу шесть решений?

Чтобы результат ранней пары не мог повлиять на решение по поздней.

## 8. Чем LessonResult отличается от DayResult?

Первый описывает одну пару, второй — все пары дня.

## 9. Чем DayResult отличается от StudentHistory?

Первый — один день, второй — список прошлых дней.

## 10. Зачем ISkipStrategy?

Runner может запускать любую реализацию общего контракта.

## 11. Почему baseline ходит на все пары?

Это простая законная стратегия без риска вылета и без скрытых знаний.

## 12. Почему результат baseline равен 100?

Сто дней дают сто пирожков; прогулок нет.

## 13. Где реализован первый день?

В `Teacher.GetAskProbability`: для зависимых правил `day == 0` даёт ноль.

## 14. Как работает XOR?

Он истинен, когда вчера спрашивали ровно по одному из A и B.

## 15. Почему Teacher использует StudentHistory, а стратегия — интерфейс?

Teacher нужны факты; стратегии — только наблюдаемая часть.

## 16. Почему программа делает 1000 прогонов?

Среднее меньше зависит от случайных правил одного семестра.

## 17. Что создаётся заново в итерации?

Teacher, стратегия, симулятор, история и результат семестра.

## 18. Как проверяется ответ стратегии?

`ValidateAttendance` проверяет `null` и длину массива.

## 19. Как обеспечено требование по производительности?

Есть `Stopwatch`; фактические 1000 прогонов заняли около 161 мс.

## 20. Что возвращает Run при вылете?

`SemesterResult` с `Pleasure = 0` и `Expelled = true`.

## 21. Почему день добавляется после всех пар?

Стратегия следующего дня должна видеть только полный законченный день.

## 22. Что осталось для отдельного конкурсного проекта?

Создать отдельный `.csproj` net10.0 и поместить туда класс стратегии, ссылающийся только на публичные контракты.

# 19. Краткая шпаргалка перед защитой

## За 2 минуты перед защитой

    TeacherFactory -> создаёт Teacher
    Teacher -> применяет правило к фактической истории
    LessonResult -> результат одной пары
    DayResult -> шесть пар одного дня
    StudentHistory -> все завершённые дни
    IReadOnlyStudentHistory -> безопасный взгляд стратегии
    ISkipStrategy -> контракт стратегии
    SemesterSimulator -> проводит 100 дней
    SemesterResult -> Pleasure + Expelled
    Program -> 1000 семестров + статистика

Главные тезисы:

1. Стратегия Teacher не получает.
2. `DecideDay` вызывается один раз до всех сегодняшних опросов.
3. `true` означает идти, `false` — прогулять.
4. `false` в `WasAsked` — известный факт, `null` — неизвестный исход.
5. Teacher читает `WasActuallyAsked`, стратегия — `WasAsked`.
6. История строится как `LessonResult → DayResult → StudentHistory`.
7. При прогулке и опросе возвращается `SemesterResult(0, true)`.
8. Baseline всегда ходит: 100 удовольствия, 0 вылетов.
9. 1000 прогонов заняли около 161 мс.
10. Все основные требования выполнены, кроме физически отдельного проекта стратегии.
